# Protobuf Contracts

This directory holds the **wire-format contracts** that bind every Velocity service together.
Treat these files as the canonical source of truth — when they change, every service must
rebuild against the new definitions.

## Files

| File | Purpose | Consumers |
|------|---------|-----------|
| [`common.proto`](common.proto) | Shared scalars: `Side`, `OrderType`, `Money`, `Timestamp` | All |
| [`telemetry.proto`](telemetry.proto) | High-volume `OrderEvent` and `FillEvent` streams on Redpanda | `bot-worker`, `telemetry-ingester`, `correctness-validator` |
| [`orchestrator.proto`](orchestrator.proto) | gRPC API between API Gateway, Submission Engine, and Bot Controller | `api-gateway`, `submission-engine`, `bot-fleet/controller` |
| [`bot.proto`](bot.proto) | Bidirectional streaming RPC between Bot Controller and Workers | `bot-fleet/controller`, `bot-fleet/worker` |
| [`scoring.proto`](scoring.proto) | Composite score record published to the leaderboard | `telemetry-ingester`, `leaderboard-ws`, `frontend` |

## Conventions

- **Package**: every file lives under `velocity.<domain>.v1` (versioned).
- **Field numbers**: never reuse — deprecate with `[deprecated = true]` instead.
- **Timestamps**: nanoseconds since Unix epoch as `int64` (`fixed64` on the hot path).
  We do **not** use `google.protobuf.Timestamp` for `OrderEvent` because the two-field encoding
  is 9 bytes vs 8 for a fixed64 — that matters when you publish millions per second.
- **Required vs optional**: proto3 has no `required`. We mark every field that must be present
  in comments and validate at the deserialization layer.
- **Generation**: regenerated by `make proto` into `proto/gen/{cpp,go,ts,py}/`. Do not edit the
  generated files — they are git-ignored. The **one exception** is the committed
  `gen/go/go.mod` stub that the Go services `replace` against; `clean` is kept
  **off** in [`buf.gen.yaml`](buf.gen.yaml) so regeneration never deletes that stub
  (a `clean: true` would wipe it and break the `submission-engine` build on the next compile).

## Why protobuf and not Avro / Cap'n Proto / FlatBuffers?

- **Protobuf** has first-class support in C++, Go, and TypeScript with mature tooling.
- **gRPC** uses protobuf natively — we get the schema + the RPC framework in one package.
- **Cap'n Proto** is faster (zero-copy) but its C++ tooling is fragile and tooling for
  schema evolution is weaker.
- **FlatBuffers** is faster on read but its codegen for Go is anemic.

When throughput matters more than schema evolution (the hot publish path from bot to
Redpanda), we use protobuf with **arena allocators** to avoid per-message `new`/`delete`.
See `OrderEvent` for the details.
